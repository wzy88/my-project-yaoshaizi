# 房间状态测试矩阵

这份矩阵用于约束最容易出现死锁、错权、假继续、假旁观的房间状态流转。

## 一、不变量

- 结算阶段在房主提交下一局安排前，`players` / `spectators` 不能因为“下局计划”而提前变化。
- 任何 `pendingBench` / `pendingSeat` 都只能代表“待生效计划”，不能直接剥夺本局输家的结算权限。
- 如果 `ownerSeatingRequired=true`，非房主不能开始下一局，但仍必须保留离开房间的出口。
- 离线 `pendingSeat` 旁观者不能阻塞下一局开始。
- 只要当前房间仍有 2 名在线桌上玩家，就不能出现“无人可继续、无人可离开”的状态。

## 二、组合场景

- 2 人局：输家未被标记 / 输家被标记下局旁观 / 赢家被标记下局旁观。
- 多人局：输家被标记下局旁观 / 非输家被标记下局旁观 / 同时存在待上桌旁观者。
- 旁观者：在线 `pendingSeat` / 离线 `pendingSeat` / 纯 `spectating`。
- 结算权限：输家在线 / 输家离线 / 房主代继续。
- 逃生路径：结算弹层可继续 / 不可继续 / 可离开。

## 三、执行层级

- `server-room-engine.test.mjs`
  - 负责状态机不变量、结算后成员集合、下一局计划的真正生效时机。
- `room-mobile-entry.test.mjs`
  - 负责房间页权限文案、按钮可见性、结算弹层逃生口、输家/房主交互结果。
- `room-service-*.test.mjs`
  - 负责 socket 事件、重连、同账号、多端、语音、倒计时等服务层回归。

## 四、关键回归命令

```bash
npm run test:critical-room-flows
```

这个命令优先覆盖最容易把用户卡死的主链路：

- 房间状态机
- 结算与下一局
- 同账号房间关系
- 倒计时
- 语音链路
