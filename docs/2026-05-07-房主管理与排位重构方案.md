# 2026-05-07 房主管理与排位重构方案

适用范围：

- 服务端状态机：`apps/server/src/engine/room-engine.ts`
- 服务端事件入口：`apps/server/src/engine/room-service.ts`
- 共享事件/类型：`packages/shared/src/types.ts`、`packages/shared/src/events.ts`
- 小程序房间页：`miniprogram/pages/room/room.*`
- 主题配套：`miniprogram/pages/room/room.wxss` 与房间主题变量体系

本文档用于统一“房主安排座位 / 旁观者 / 下局旁观 / 顺逆时针 / 每局开始前排位”这套逻辑，避免继续在现有 `waitingPlayers` 模型上局部补洞。

## 1. 目标

- `安排座位` 对房主常驻，不再只是“有人等入座时才出现”的临时入口。
- 游戏进行中，房主可以管理“下局谁上桌、谁旁观”，但不破坏当前局状态。
- 每局开始前，房主可以统一完成：
  - 桌上/旁观人员编排
  - 全员座位调整
  - 顺时针 / 逆时针确认
- 多个旁观者时，不要求房主机械地一个个往空座位里塞；系统先自动补空座，房主只做最终微调。
- “纯旁观”不阻塞下一局；只有“待上桌但未编排完成”的人，才阻塞下一局。

## 2. 核心问题

当前逻辑把两类人混在了同一个 `waitingPlayers` 里：

1. 中途加入、准备下局上桌的人
2. 纯旁观、不打算立刻回桌的人

这会导致两个问题：

- 只要房间里存在旁观者，结算后就容易把所有人都卡在“等房主安排座位”。
- 房主把某个人移到旁观后，如果还是落到同一类状态，就会让后续每局都被无意义阻塞。

## 3. 推荐模型

推荐把参与者拆成三类，而不是只保留 `players + waitingPlayers`：

### 3.1 `players`

当前在桌上、参与本局的玩家。

### 3.2 `spectators`

纯旁观者，不阻塞下一局。

来源包括：

- 中途加入但暂时不申请回桌的人
- 被房主移到旁观的人
- 暂时离席但保留房间会话的人

### 3.3 `pendingSeat`

准备下局回桌的人，会阻塞下一局，直到房主完成排位。

来源包括：

- 中途加入并申请下局上桌的人
- 被房主从旁观列表里点了“下局上桌”的人

### 3.4 `pendingBench`

游戏进行中，房主把某个桌上玩家标记为“下局旁观”。

注意：

- 本局进行中，不直接把该玩家从 `players` 剔除。
- 只在下一局开始前的排位编排里真正生效。

## 4. 阻塞下一局的正确条件

不要再用：

- “房间里有旁观者”

来判断是否必须安排座位。

应该改成：

- 存在 `pendingSeat`
- 或当前存在未提交完成的排位草稿

才阻塞下一局。

这意味着：

- `spectators` 可以存在很多轮，不影响下一局开始。
- 只有真正准备回桌的人，才要求房主完成安排。

## 5. 阶段规则

### 5.1 `ready`

房主打开 `安排座位` 后，可以：

- 调整桌上所有人的座位
- 把桌上玩家移到旁观
- 把旁观者拉回桌上
- 改顺时针 / 逆时针
- 一键自动补空座

### 5.2 `ended`

与 `ready` 一样，视为“下一局开始前排位态”。

- 所有上一局的 `pendingBench` 在这里落地生效
- 所有 `pendingSeat` 在这里等待房主确认最终排位

### 5.3 `rolling / calling / opening`

房主仍然可以点 `安排座位`，但打开的是“本局中管理态”，只能：

- 把桌上玩家标记为 `下局旁观`
- 取消 `下局旁观`
- 把某个旁观者标记为 `下局上桌`
- 取消 `下局上桌`

此阶段不能：

- 改座位
- 改顺时针 / 逆时针
- 立刻让桌上玩家消失

原因很简单：

- 当前局的行动顺序、骰子、叫牌、开牌归属都依赖当前 `players`
- 中途直接改桌上身份会破坏本局状态机

## 6. 自动补空座规则

进入 `ready / ended` 的统一排位面板时，系统先自动生成一份草稿：

1. 以当前桌上玩家为基础
2. 去掉已经标记 `pendingBench` 的人
3. 再把 `pendingSeat` 玩家按顺序补进空座

建议默认顺序：

- 先按进入 `pendingSeat` 的时间顺序
- 若缺时间戳，则按加入房间时间或昵称稳定排序

注意：

- 这是草稿，不是最终结果
- 房主之后仍可手动微调

## 7. 从桌上移到旁观、再加回来

### 7.1 从桌上移到旁观

游戏进行中：

- 点 `下局旁观`
- 该玩家进入 `pendingBench`
- 本局继续留在桌上

下一局编排时：

- 从桌上名单移除
- 进入 `spectators`

### 7.2 再加回来

不要自动回桌。

如果房主要把他加回来：

- 在旁观列表点 `下局上桌`
- 该玩家进入 `pendingSeat`
- 到局前排位阶段进入自动补位草稿

这样可以保证：

- “移去旁观”是有效控制，不会自动反弹
- 是否阻塞下一局，取决于他是不是 `pendingSeat`

## 8. 面板设计

推荐同一个入口，两个模式。

## 8.1 本局中管理态

用途：

- 管理“下局谁上 / 谁下”
- 不改当前局座次

草图：

```text
+--------------------------------------------------+
|  房主管理                                         |
|  本局进行中：当前只支持管理下局人员               |
|                                                  |
|  [桌上玩家]                                       |
|  P1 房主      座位1    [保持在桌]                 |
|  P2 玩家二    座位2    [下局旁观]                 |
|  P3 玩家三    座位3    [下局旁观]                 |
|                                                  |
|  [旁观者]                                         |
|  S1 小王      纯旁观   [下局上桌]                 |
|  S2 小李      纯旁观   [下局上桌]                 |
|                                                  |
|  说明：                                           |
|  - 本局中不能换座位                               |
|  - 本局中不能改顺逆时针                           |
|  - 上述变更将于下一局开始前生效                   |
|                                                  |
|                   [完成]                          |
+--------------------------------------------------+
```

设计建议：

- 顶部说明文案必须直白，避免房主误以为当前局会立即换人
- `下局旁观` 用危险色，但不要做成不可逆红色破坏按钮
- `下局上桌` 用积极色
- 已标记项需要显示 `下局生效` 小标记

## 8.2 局前排位态

用途：

- 真正决定下一局整桌排位
- 统一微调顺序和座位

草图：

```text
+--------------------------------------------------+
|  安排座位                                         |
|  下一局开始前统一排位                             |
|                                                  |
|  [入座方向]  ( 顺时针 )   ( 逆时针 )              |
|                                                  |
|  [待上桌 / 旁观]                                  |
|  待上桌                                           |
|  - 小王   [移上桌草稿中]                          |
|  - 小李   [移上桌草稿中]                          |
|                                                  |
|  旁观中                                           |
|  - 小赵   [下局上桌]                              |
|  - 小陈   [保持旁观]                              |
|                                                  |
|  [8个座位]                                        |
|  1号 房主        2号 小王                         |
|  3号 空          4号 玩家二                       |
|  5号 小李        6号 玩家三                       |
|  7号 空          8号 玩家四                       |
|                                                  |
|  操作：                                           |
|  - 点桌上玩家 -> 点目标座位：移动/交换            |
|  - 点桌上玩家 -> 移到旁观：下桌                   |
|  - 点待上桌玩家 -> 点目标空座：入座               |
|                                                  |
|  系统已自动补空座，你可以继续微调                 |
|                                                  |
|        [恢复默认补位]   [完成安排并开始]          |
+--------------------------------------------------+
```

设计建议：

- 保留现有 `seat-grid`，不用推翻重做
- 左侧是人员池，右侧是 8 个座位
- “恢复默认补位”很有用，房主乱改后可以一键回到系统草稿
- 主按钮建议直接叫 `完成安排并开始`
- 如果人数还不满足开局条件，则主按钮改成 `完成安排`

## 8.3 为什么不建议继续用“先选等待者，再输空座号”

因为它不符合真实牌桌心智：

- 房主想的是“排整桌”
- 不是“先往空位里塞一个人”

多人旁观时，这种输入式流程会非常笨重，而且与后续换座、改方向是割裂的。

## 9. 主题配套建议

这次不建议为每个主题单独写一套结构，只建议做“同结构、多主题变量”。

需要补齐的主题状态包括：

- 面板底色
- 面板描边 / 光晕
- 选中态
- `下局上桌` 正向按钮态
- `下局旁观` 危险按钮态
- 待生效标签态
- 顺/逆时针切换态
- 主按钮 / 次按钮态

推荐做法：

- 在 `room.wxss` 增加一组房主管理面板变量
- 各主题只覆盖颜色、描边、阴影、标签态
- 结构仍复用统一类名

建议变量名示意：

```css
--owner-sheet-bg
--owner-sheet-border
--owner-accent
--owner-accent-soft
--owner-danger
--owner-danger-soft
--owner-pending-chip
--owner-seat-selected
--owner-seat-target
```

## 10. 事件与数据建议

当前事件过于碎片化：

- `room:seat:set`
- `room:seat:swap`
- `room:waiting:admit`

推荐改成两类事件：

### 10.1 `room:participant:plan`

用于游戏进行中，记录下局人员意图：

- 哪些桌上玩家 `pendingBench`
- 哪些旁观者 `pendingSeat`

### 10.2 `room:seating:commit`

用于 `ready / ended`，一次提交完整排位结果：

- 最终桌上玩家列表
- 每个玩家最终座位
- 最终方向 `cw/ccw`

推荐不要再让前端靠多次小事件拼最终结果。

## 11. 推荐执行顺序

如果正式开改，建议严格按这个顺序推进：

1. 先改共享类型和事件定义
2. 再改服务端状态模型
3. 再改服务端校验与广播
4. 再改小程序数据结构
5. 再改房主管理面板交互
6. 最后补主题和样式状态

不要反过来从页面先改，否则 UI 会先跑偏。

## 12. 测试矩阵

至少要覆盖以下场景：

### 12.1 局前排位

- 无旁观者时，房主可直接调座位与方向
- 有多个 `pendingSeat` 时，自动补空座草稿正确
- 房主可继续交换/移动/移去旁观
- `完成安排并开始` 后，服务端玩家顺序与方向正确

### 12.2 本局中管理

- 房主可把桌上玩家标记 `下局旁观`
- 房主可取消 `下局旁观`
- 房主可把旁观者标记 `下局上桌`
- 本局中不能改座位与方向

### 12.3 结算后进入下一局

- 存在 `pendingSeat` 时，下一局被阻塞并要求房主编排
- 只有 `spectators`、没有 `pendingSeat` 时，不阻塞下一局
- `pendingBench` 在局前排位态正确落地为 `spectators`

### 12.4 极端场景

- 多个旁观者、多个空座
- 有人被标记下局旁观后又立即取消
- 有人从旁观被标记下局上桌后又取消
- 房主在编排过程中断线重连
- 房主编排提交时，某个待上桌者已离线

## 13. 结论

这套逻辑值得做，但前提是：

- 不再沿用“有 waiting 就拦下一局”的旧模型
- 从模型上把 `spectators` 和 `pendingSeat` 区分开
- 把房主常驻入口做成“同入口、双模式”的统一管理面板

推荐最终方向：

- 游戏中：管理下局人员，不碰当前局座次
- 局前：统一排位、统一方向、统一开始

这是目前最顺、最稳、最像真实牌桌的一版。

## 14. 已确认决议

以下 6 条已确认，后续实现按此执行，不再反复摇摆：

1. `安排座位` 对房主常驻。
   - 游戏中也能点开，但此时只支持“下局生效”的人员管理。

2. 游戏中把桌上玩家移到旁观，不立即生效。
   - 只标记为 `下局旁观`，当前局不动。

3. 旁观者拆成两类。
   - `spectating`：纯旁观，不阻塞下一局。
   - `pendingSeat`：下局上桌，阻塞下一局直到房主完成排位。

4. 每局结束后，系统会先把 `pendingSeat` 玩家自动补进空座，生成一份排位草稿。
   - 房主只需要在此基础上微调。

5. 房主把人移去旁观后，不会自动回桌。
   - 只有房主再次点 `下局上桌`，该玩家才会重新进入 `pendingSeat`。

6. 局前排位完成后的主按钮使用：
   - `完成安排并开始`

## 15. 事件与状态字段变更清单

这部分用于正式开发前锁定数据结构，不等于最终代码名字必须 100% 一致，但语义必须一致。

### 15.1 共享类型建议

当前：

- `RoomPhase = "ready" | "rolling" | "calling" | "opening" | "ended"`
- `waitingPlayers: WaitingPlayerState[]`

建议：

1. 先保留现有 `RoomPhase`
   - 不新增阶段，先通过“同入口双模式 + 阶段内能力差异”落地。

2. 把 `waitingPlayers` 拆分为两组或一组带状态的参与者

方案 A：双数组

- `spectators: SpectatorState[]`
- `pendingSeats: PendingSeatState[]`

方案 B：单数组带状态

- `spectators: Array<{ ..., seatIntent: "spectating" | "pendingSeat" }>`

当前更推荐方案 B，原因：

- 前端更容易统一渲染“旁观池”
- 服务端迁移成本更低
- “纯旁观”和“准备回桌”只差一个状态位

3. 桌上玩家增加下局意图字段

- `nextRoundIntent?: "stay" | "bench"`

或独立字段：

- `pendingBench: boolean`

当前更推荐独立布尔字段，便于回归测试。

### 15.2 客户端事件建议

当前主路径事件：

- `room:seat:set`
- `room:seat:swap`
- `room:waiting:admit`

建议替换为：

1. `room:participant:plan`
   - 仅用于游戏中
   - 表达“下局旁观 / 取消旁观 / 下局上桌 / 取消上桌”

建议载荷示意：

```ts
{
  playerId: string;
  target: "bench" | "stay" | "seat" | "spectate";
}
```

语义示意：

- 桌上玩家：`bench` / `stay`
- 旁观者：`seat` / `spectate`

2. `room:seating:commit`
   - 仅用于 `ready / ended`
   - 一次提交完整排位草稿

建议载荷示意：

```ts
{
  direction: "cw" | "ccw";
  seatedPlayerIds: Array<{
    playerId: string;
    seatIndex: number;
  }>;
  spectatorPlayerIds: string[];
}
```

要求：

- 服务端一次校验
- 一次落地
- 一次广播

不再允许前端靠多次小事件拼最终结果。

### 15.3 服务端状态机规则

1. 本局中 `room:participant:plan`
   - 只改下局意图，不改当前 `players` 排列

2. 进入 `ended`
   - 若存在 `pendingSeat`，阻塞下一局
   - 若只有 `spectating`，不阻塞下一局

3. 打开局前排位时
   - 服务端不需要持久保存前端草稿
   - 只需要在 `room:state` 中给足够数据，让前端能生成稳定草稿

4. 提交 `room:seating:commit`
   - 校验座位唯一
   - 校验人数不超过 8
   - 校验 `pendingSeat` 玩家要么上桌，要么仍明确留在旁观
   - 校验 `bench` 玩家不再占用桌上座位
   - 落地新方向与新座位

  - 自动补空座草稿
  - 完成安排并开始

## 17. 风险判断

这次改造的真正风险不在视觉，而在：

- 旧 `waitingPlayers` 逻辑已经深入 `startGame()` / `restartRound()` / 房主主按钮状态
- 旧页面代码默认“旁观者 = 等待安排入座者”
- 旧测试里也大量使用了这个前提

所以：

- 这次必须按“模型先变、事件再变、页面最后变”的顺序推进
- 不建议先改 UI 再倒逼服务端
