# 2026-05-07 房主管理与排位重构 - 代码级变更清单

配套方案文档：

- [2026-05-07-房主管理与排位重构方案.md](/Users/wzy/Desktop/CodeX-20260303/摇骰子/docs/2026-05-07-房主管理与排位重构方案.md)

本文档不再讨论“产品上该不该这样做”，只回答三件事：

1. 这次具体要改哪些文件
2. 每个文件改什么
3. 正式开发时必须遵守什么顺序

## 1. 总体原则

- 先改共享类型和事件，再改服务端，再改小程序页面，最后收主题样式和回归。
- 不在旧 `waitingPlayers + room:waiting:admit + room:seat:set/swap` 上继续加补丁。
- 以“同入口双模式”的房主管理面板替换现有“等待入座 + 排位设置”割裂交互。

## 2. 共享层改造

### 2.1 [packages/shared/src/types.ts](/Users/wzy/Desktop/CodeX-20260303/摇骰子/packages/shared/src/types.ts)

当前问题：

- `RoomPhase` 足够，但房间状态只暴露 `waitingPlayers`
- 事件模型仍围绕：
  - `room:seat:set`
  - `room:seat:swap`
  - `room:waiting:admit`

需要改动：

1. 新增或重构旁观池类型

建议新增：

```ts
type SpectatorIntent = "spectating" | "pendingSeat";

interface SpectatorState {
  id: string;
  accountId?: string;
  accountDisplayId?: string;
  nickname: string;
  avatar: string;
  onlineStatus: "online" | "offline";
  seatIntent: SpectatorIntent;
  joinedAt?: number;
}
```

2. 桌上玩家补“下局旁观”标记

建议给 `PlayerState` 增加：

```ts
pendingBench?: boolean;
```

3. `RoomStateDTO` 重构

当前：

```ts
players: PlayerState[];
waitingPlayers: WaitingPlayerState[];
```

建议：

```ts
players: PlayerState[];
spectators: SpectatorState[];
```

4. 新增客户端事件

建议新增：

```ts
"room:participant:plan": {
  playerId: string;
  target: "bench" | "stay" | "seat" | "spectate";
};

"room:seating:commit": {
  direction: "cw" | "ccw";
  seatedPlayerIds: Array<{
    playerId: string;
    seatIndex: number;
  }>;
  spectatorPlayerIds: string[];
};
```

5. 废弃旧事件

建议正式替换：

- 删除主路径依赖：
  - `room:seat:set`
  - `room:seat:swap`
  - `room:waiting:admit`

保留方式：

- 可以先保留类型定义一个过渡周期
- 但房间页不再发这些事件

### 2.2 [packages/shared/src/events.ts](/Users/wzy/Desktop/CodeX-20260303/摇骰子/packages/shared/src/events.ts)

需要改动：

- `CLIENT_EVENTS` 删除：
  - `room:seat:set`
  - `room:seat:swap`
  - `room:waiting:admit`
- `CLIENT_EVENTS` 新增：
  - `room:participant:plan`
  - `room:seating:commit`

注意：

- 如果服务端做过渡兼容，这里可以短期保留旧事件
- 但正式清理时必须跟房间页一起下掉

## 3. 服务端状态机改造

### 3.1 [apps/server/src/engine/room-engine.ts](/Users/wzy/Desktop/CodeX-20260303/摇骰子/apps/server/src/engine/room-engine.ts)

这是本次核心文件。

当前风险点：

- `waitingPlayers` 深度参与：
  - `startGame()`
  - `restartRound()`
  - `ownerRestartRequired`
  - `admitWaitingPlayer()`
- 当前逻辑默认“有 waiting 就可能阻塞下一局”

必须改的区域：

#### A. 内部状态字段

当前：

```ts
private waitingPlayers = new Map<string, WaitingPlayerState>();
private ownerRestartRequired = false;
```

建议改成：

```ts
private spectators = new Map<string, SpectatorState>();
private ownerRestartRequired = false;
```

补充说明：

- `ownerRestartRequired` 继续保留，但语义要改
- 它不再表示“有 waiting”
- 而表示“存在待处理的下一局编排需求”

#### B. 入房流程

当前 `addWaitingPlayer()` 需要拆义：

- 中途加入的人默认进入 `spectators`
- 其默认 `seatIntent` 如何定，需要统一

推荐：

- 中途加入默认 `seatIntent = "pendingSeat"`
  - 因为此人通常是准备下局玩的
- 被房主移去旁观的人默认 `seatIntent = "spectating"`

这意味着：

- 不能简单复用旧 `addWaitingPlayer()`
- 建议改成：
  - `addSpectator(input, intent)`

#### C. 阻塞条件

当前关键逻辑：

- `getOnlineWaitingPlayerCount()`
- `startGame()` / `restartRound()` 用它判断是否拒绝开始

必须替换成：

- `getOnlinePendingSeatCount()`

含义：

- 只统计 `seatIntent === "pendingSeat"` 且在线的人

直接受影响的方法：

- `startGame()`
- `restartRound()`
- `openDice()` 结束后设置 `ownerRestartRequired` 的地方

#### D. 新的“下局意图”接口

新增方法建议：

- `planParticipant(actorId, playerId, target)`
- `commitSeating(actorId, payload)`

其中：

1. `planParticipant(...)`
   - 游戏中调用
   - 只改：
     - 玩家 `pendingBench`
     - 旁观者 `seatIntent`

2. `commitSeating(...)`
   - `ready / ended` 调用
   - 一次落地：
     - 桌上玩家最终名单
     - 旁观者最终名单
     - 最终方向
     - 最终座位

#### E. 结束后落地规则

结算后需要统一处理：

1. 把 `pendingBench === true` 的桌上玩家移出桌上
2. 这些人进入 `spectators`
3. 状态记为 `seatIntent = "spectating"`
4. 计算当前是否还存在 `pendingSeat`
5. 决定是否阻塞下一局

这一段建议做成独立私有方法，例如：

- `prepareNextRoundParticipants()`

#### F. `getState()` 输出

必须调整成输出新结构：

- `players`
- `spectators`

同时：

- `players` 要带 `pendingBench`
- `spectators` 要带 `seatIntent`

### 3.2 旧方法处理策略

这些旧方法建议直接删掉或退化成兼容壳：

- `setSeat()`
- `swapSeats()`
- `admitWaitingPlayer()`
- `getOnlineWaitingPlayerCount()`

最稳的做法：

- 正式实现时不再让业务主路径调用它们
- 若要短期兼容，可让它们内部转向新逻辑，但最好尽早删

## 4. 服务端事件入口改造

### 4.1 [apps/server/src/engine/room-service.ts](/Users/wzy/Desktop/CodeX-20260303/摇骰子/apps/server/src/engine/room-service.ts)

需要改的区域很明确：

#### A. `switch` 分发入口

当前还分发：

- `room:seat:set`
- `room:seat:swap`
- `room:waiting:admit`

需要改成：

- `room:participant:plan`
- `room:seating:commit`

#### B. 具体 handler

新增：

- `handleRoomParticipantPlan(...)`
- `handleRoomSeatingCommit(...)`

删除或废弃：

- `handleRoomSeatSet(...)`
- `handleRoomSeatSwap(...)`
- `handleRoomWaitingAdmit(...)`

#### C. 创建/加入逻辑里的总人数判断

当前有：

```ts
const participantCount = roomState.players.length + roomState.waitingPlayers.length;
```

必须统一替换成：

```ts
const participantCount = roomState.players.length + roomState.spectators.length;
```

#### D. 重连恢复逻辑

当前有很多地方判断：

- 玩家是否在 `players`
- 玩家是否在 `waitingPlayers`

都要改成：

- 玩家是否在 `players`
- 玩家是否在 `spectators`

受影响点包括：

- 恢复绑定
- 私骰重发
- 会话清理
- 自己是否仍在房间中的判断

## 5. 小程序数据与交互改造

### 5.1 [miniprogram/pages/room/room.js](/Users/wzy/Desktop/CodeX-20260303/摇骰子/miniprogram/pages/room/room.js)

这是客户端核心文件。

当前问题：

- 页面数据仍使用：
  - `waitingPlayersRaw`
  - `waitingPlayerCount`
  - `selfIsWaiting`
- 主按钮、等待文案、排位入口都围绕“等待入座”建模
- `openWaitingAdmitFlow()` 仍是单人入座式流程

需要改的块：

#### A. data 字段重构

建议新增或替换：

- `spectatorsRaw`
- `pendingSeatCount`
- `selfIsSpectating`
- `selfSeatIntent`
- `ownerSeatingMode`
  - `"live"` 本局中管理态
  - `"staging"` 局前排位态
- `seatingDraft`
  - 包含草稿方向、草稿座位、草稿旁观池

建议逐步下掉：

- `waitingPlayersRaw`
- `waitingPlayerCount`
- `selfIsWaiting`

#### B. `room:state` 派生逻辑

当前围绕：

- `waitingPlayersRaw.filter(online)`
- `selfIsWaiting`
- `primaryActionText = "安排入座" / "等待房主安排"`

需要改成：

1. 从 `spectatorsRaw` 派生：
   - `pendingSeatCount`
   - `onlineSpectatorCount`
   - `selfSeatIntent`

2. 主按钮规则改为：
   - 若存在 `pendingSeatCount > 0` 且当前是局前：房主显示 `安排座位`
   - 若只有纯旁观者：不阻塞下一局
   - 非房主且有待编排人员时：显示 `等待房主安排`

#### C. 顶部入口

当前 WXML 里：

- 菜单中的 `排位设置` 只在 `ready/ended` 显示
- 桌上的 `等待入座(n)` 只在 `ready/ended` 显示

对应 JS 也按这个建模。

需要改成：

- 房主左上角入口常驻
- 不再依赖“有 waiting 才出现”
- 点击后根据 `phase` 决定打开：
  - 本局中管理态
  - 局前排位态

#### D. 删除旧单人入座流程

需要下掉：

- `openWaitingAdmitFlow()`
- 现有“选等待者 -> 选空座号”的链路

同时下掉：

- 相关 toast 文案
- 相关 ack 分支里的 `room:waiting:admit`

#### E. 新增草稿编排逻辑

建议新增一组 helper：

- `buildAutoSeatingDraft(...)`
- `applyBenchAndPendingSeatToDraft(...)`
- `moveDraftPlayerToSeat(...)`
- `moveDraftPlayerToSpectators(...)`
- `swapDraftSeats(...)`
- `commitSeatingDraft(...)`

用途：

- 局前排位态只操作本地草稿
- 点 `完成安排并开始` 才统一发送 `room:seating:commit`

#### F. 本局中管理逻辑

建议新增方法：

- `openOwnerManagePanel()`
- `togglePlayerBenchIntent(playerId)`
- `toggleSpectatorSeatIntent(playerId)`

这些方法只发：

- `room:participant:plan`

不再改当前局座位。

### 5.2 [miniprogram/pages/room/room.wxml](/Users/wzy/Desktop/CodeX-20260303/摇骰子/miniprogram/pages/room/room.wxml)

## 7. 开发顺序

这次正式开改时，必须按以下顺序：

1. `packages/shared/src/types.ts`
2. `packages/shared/src/events.ts`
3. `apps/server/src/engine/room-engine.ts`
4. `apps/server/src/engine/room-service.ts`
5. `tests/server-room-engine.test.mjs`
6. `miniprogram/pages/room/room.js`
7. `miniprogram/pages/room/room.wxml`
8. `miniprogram/pages/room/room.wxss`
9. `tests/room-mobile-entry.test.mjs`
10. `tests/room-entry-layout.test.mjs`

不要打乱顺序。

原因：

- 共享层不先改，服务端/前端都会反复返工
- 服务端不先稳定，前端状态草稿会失去依托
- 页面结构不稳定前，样式没有意义

## 8. 这一步完成的定义

只有同时满足下面三点，才算这次逻辑改造真正完成：

1. 房主左上角入口常驻
2. `spectating / pendingSeat / pendingBench` 三类语义全部打通
3. 旧 `waitingPlayers` 主路径不再控制下一局阻塞逻辑

如果只是做到了其中一两项，都不算完成。
