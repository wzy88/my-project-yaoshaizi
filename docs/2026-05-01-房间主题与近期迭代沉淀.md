# 2026-05-01 房间主题与近期迭代沉淀

这份文档用于把最近一轮房间主题、房间流程、兼容性和测试补强沉淀下来。后续新增主题或继续迭代房间逻辑时，优先看这里和 `dice-room-theme-maintainer` skill。

## 主题现状

- 当前主题 id 是 `jade-green`、`ruby-red`、`imperial-red`、`glacier-blue`。
- `jade-green` 是默认青绿色基础主题，主要复用 `miniprogram/assets/figma-room-v2/` 下的通用骰子和房间视觉。
- `ruby-red` 的用户侧含义是黑色主题，展示名为“玄曜”，资产集中在 `miniprogram/pages/room/assets/room-themes/`。
- `imperial-red` 的用户侧含义是红金主题，展示名为“绛华”，当前使用红金背景、红系主题骰面，以及偏玉质的叫骰/开牌/骰盅 SVG 切片。
- `glacier-blue` 的用户侧含义是冰蓝主题，展示名为“霁雪”，当前使用冰晶背景、冰蓝骰面、冰蓝杯体和珊瑚色强调按钮。

## 主题资产路径

近期已把房间专属主题素材从全局 `miniprogram/assets/room-themes/` 迁到房间分包内：

- 主题素材：`miniprogram/pages/room/assets/room-themes/`
- 房间音效：`miniprogram/pages/room/assets/audio/`
- 代码引用统一使用 `/pages/room/assets/...` 绝对小程序路径。

这么做是为了让房间分包自带重素材，降低主包压力，也避免真机和开发者工具在跨包资源路径上的不一致。

旧主包路径 `miniprogram/assets/room-themes/` 和 `miniprogram/assets/audio/` 不再作为运行资源入口；新增素材不要放回这些目录。房间分包里也只保留被 `room-theme-assets.js`、`dice-assets.js` 或服务端 manifest 引用的主题素材。

## 远程主题 manifest

本轮开始，服务端是房间主题配置权威：

- `apps/server/src/engine/room-theme-catalog.ts` 维护主题 id、展示名、版本、资源路径、加载文案和关键资源列表。
- `GET /api/room-theme-manifests` 返回全部主题 manifest。
- `GET|POST /api/room-theme-manifest` 返回单个主题 manifest。
- 创建房间时服务端把主题锁定为 `themeId + themeVersion`，后续 `action:ack` 和 `room:state` 都会下发完整 `themeManifest`，避免不同玩家看到不同主题版本。
- 设置 `DICE_ROOM_THEME_CDN_BASE_URL` 后，服务端会把房间分包资源路径改写为远程 CDN 路径；不设置时继续返回本地分包路径。

小程序侧由 `miniprogram/utils/room-theme-loader.js` 负责加载：

- 创建页选择主题后先预取 manifest 和关键资源。
- 进房前显示加载遮罩，同步 manifest、下载远程资源并缓存到本地文件。
- 加载成功后把 manifest 运行时注册进 `room-theme-assets.js` 和 `dice-assets.js`。
- 请求失败、下载失败或缓存不可用时，自动回退到内置分包资源，不阻塞进房。

房间内加载入口统一使用 `room-theme-loader` 这一套遮罩。主题资源未准备好、主题资源加载中，以及连接成功前的创建/加入 pending 状态，都复用同一个骰子加载动画和文案区域；不要再新增另一套房间加载页、悬浮 loading 或风格不一致的中转页面。

## 新增主题时必须同步的位置

新增、删除或重命名主题时，不要只替换图片。以下位置需要保持一致：

- `packages/shared/src/types.ts`：`RoomThemeId` 类型。
- `apps/server/src/engine/room-theme-catalog.ts`：后端主题目录、版本、资源 manifest 和 CDN 改写。
- `apps/server/src/engine/room-engine.ts`：房间创建时锁定主题 id 和版本。
- `apps/server/src/engine/room-service.ts`：`action:ack` 和 `room:state` 下发主题 manifest。
- `miniprogram/utils/room-themes.js`：主题 id、展示名、随机主题、CSS class 生成。
- `miniprogram/utils/room-theme-assets.js`：菜单图标、主按钮、开牌按钮、背景、骰盅、桌布、按钮 class。
- `miniprogram/utils/room-theme-loader.js`：本地 fallback、远程 manifest、文件缓存和运行时注册。
- `miniprogram/utils/dice-assets.js`：主题私有骰面 1-6 映射。
- `miniprogram/pages/create-room/create-room.js`、`.wxml`、`.wxss`：创建页主题卡片预览与文案。
- `miniprogram/pages/room/room.wxml`、`.wxss`：房间实际渲染、主题 class、主题状态样式。
- `tests/create-room-layout.test.mjs`、`tests/room-theme-manifest.test.mjs`、`tests/room-dice-assets.test.mjs`、`tests/room-mobile-entry.test.mjs`、`tests/room-entry-layout.test.mjs`、`tests/miniprogram-package-size.test.mjs`：主题路径、manifest、预览、房间状态、包体检查。

## 主题拓展规则

- 主题 id 用稳定英文短横线命名，例如 `midnight-blue`，不要用中文或临时名。
- 用户看到的是 `ROOM_THEME_LABELS` 里的中文名；不要让 `ruby-red` 这种历史 id 直接出现在 UI。
- 主题素材优先放在房间分包路径 `miniprogram/pages/room/assets/room-themes/`。
- 可直接在 WXML 里以 `<image src="{{roomThemeAssets.xxx}}">` 加载的素材，优先通过 `room-theme-assets.js` 显式映射。
- WXSS 里确实要用图片时，确认真机可加载；后续主题尽量减少散落的 `url(...)`。
- 切片按钮只隐藏对应主题变体内的通用 icon/text，不要全局隐藏 `.room-fab` 或 `.room-fab-secondary` 文本。
- 主题骰面建议继续用 SVG，测试需要验证 1-6 面完整、点数可见、颜色不会被旧主题残留污染。
- 新主题不要改座位坐标、按钮位置、桌面层级或交互流程；主题工作优先是资产、颜色、明暗、边框和状态样式替换。

## 可变现主题视觉原则

杯子、骰子和房间主题后续会承担变现价值，所以限免/付费主题不能只是换色。用户必须在房间里一眼看出“这是一套更高级的主题资产”，但这种高级感不能影响核心玩法可读性。

### 1. 默认主题和付费主题要拉开层级

- `jade-green`/青岚作为默认主题，应该干净、耐看、克制，不要做得过于华丽。
- 限免或付费主题要明显更“贵”：材质、杯口、骰面、按钮、桌布需要成套，而不是只有背景变色。
- 主题差异优先通过材质语言建立：黑曜石、暗金、红漆、玉石、冰晶、银蓝等，而不是只调 hue。
- 付费感来自“完整物件”的质感：杯口、杯身、底座阴影、反光、纹样、骰面边框都要有一致来源。

### 2. 本人 6 点钟杯子的两态规则

6 点钟方向的本人杯子是主题变现最重要的展示位，但它有两个完全不同的职责：

- 未遮住/open：服务看骰子。杯子只保留轻薄杯口、边缘主题色、底部阴影和少量高光，不能遮挡骰面，不能抢视觉。
- 已遮住/covered：服务主题展示。骰子退到后层，杯体成为主角，这时才展示完整材质、金属边、玉石/黑曜/红漆质感、纹样和更重阴影。
- 不要把“贵”堆在 open 态。open 态过重会影响玩家读骰子，也会让界面显得乱。
- covered 态要有明显的展示瞬间，让用户感觉“我买的主题在这里被看见了”。
- `已遮住` 状态文案要像小徽标，不要像便宜贴纸压在杯体正中；状态要清楚，但不能破坏杯子材质。

### 3. 杯子和骰子必须成套

- 黑色/玄曜方向：黑曜石、深黑半透、暗金杯口、低饱和红棕或金属点数。
- 红金/绛华方向：红漆或红玉杯身、金边、少量翡翠/玉质点缀、红金或玉白金点骰子。
- 默认/青岚方向：青玉或青瓷感即可，不要超过付费主题的华丽程度。
- 冰蓝/霁雪方向：冰晶、霜面玻璃、银蓝边缘和少量珊瑚色强调，不能做成普通蓝色换皮。
- 如果新增主题，例如冰蓝、水晶、紫金、赛博、国风等，先定义“杯子材质 + 骰子材质 + 桌面材质”三件套，再做 UI 色彩。
- 主题骰子要能在深浅桌面上都读清楚；小骰子不要加过重阴影，避免真机发糊。
- 骰子点数和骰子本体必须有足够明度反差。小尺寸房间骰子、叫牌面板骰子都要先保证点数可读，再谈材质高光。
- 点数质感可以用内阴影、微高光、材质色建立，但主点色不要贴近骰面底色；高光只辅助“贵”，不能承担“可读”。

### 4. 面板和按钮也要成套

房间里的菜单、叫骰面板、设置面板、排位面板、规则/历史/结算面板、顶部小按钮、关闭按钮、主次操作按钮，都属于主题资产的一部分。付费主题如果只换背景、杯子和骰子，面板还是通用深色，会显得不配套。

- 面板和按钮要跟杯子、骰子、桌布使用同一套材质语言，而不是只把通用面板调亮或调暗。
- 通用深色面板只能作为兜底；主题样式要在 `room.wxss` 后段用最终覆盖层压住旧样式。
- 主题覆盖只改背景、边框、阴影、文字色、状态色、透明度和高光，不改按钮位置、尺寸、间距、绑定、交互和逻辑。
- 完整图片切片按钮优先保留素材本身，CSS 只补文字、投影或非切片态，避免把透明切片按钮重新刷成普通渐变。
- `jade-green`/青岚作为默认主题，面板干净克制，偏青玉和铜金；`ruby-red`/玄曜偏黑曜石和暗金；`imperial-red`/绛华偏红漆、宫廷金边和玉点；`glacier-blue`/霁雪偏冰晶、银蓝和珊瑚强调。
- 选择态、已选座位、叫骰选项、结算赢家、等待入座和危险按钮也要有主题色，不要只保留默认金色。
- 叫牌面板的可选/不可选必须明显分层。数字和点数按钮不可选时不能只靠降低透明度，要有灰化、弱边框、条纹或斜杠这类“锁定感”，同时保持可选项亮度和边框清楚。

### 5. 实现优先级

视觉试验阶段可以先用 WXSS 叠渐变、边框、伪元素和阴影快速验证方向；方向确认后，适合沉淀为资产化方案：

- `selfCupOpenSrc`：未遮住时的轻量杯口/边缘层。
- `selfCupCoveredSrc`：遮住后的完整展示杯体。
- `seatCupSrc`：桌面小杯皮肤。
- `diceFaceSrc`：1-6 主题骰面。

最终更推荐把本人杯拆成后层杯体、中层骰子、前层杯口/盖杯/高光。这样 open 态能看清骰子，covered 态能完整展示主题资产。

### 6. 做主题时的检查口径

- 先问：这个主题是否有明确材质，而不只是颜色？
- 再看：open 态骰子是否仍是视觉主角？
- 再看：covered 态杯子是否比默认主题明显更贵？
- 再看：杯子、骰子、按钮、桌布、气泡是否属于同一个主题世界？
- 再看：顶部菜单、设置、排位、规则、历史、结算、叫骰面板、主次按钮是否也属于同一个主题世界？
- 再看：骰子点数在小尺寸和叫牌面板里是否一眼可读，禁用按钮是否和可选按钮有明确差别？
- 再看：房间加载是否只使用统一的 `room-theme-loader`，没有混入另一套页面或动画？
- 最后看：有没有改到座位、等待、旁观、入座、叫骰、开牌等逻辑；主题工作默认不碰这些。

## 房间等待与入座规则

近期房间旁观/等待逻辑的基线如下：

- 房间容量按总参与者计算：`players + waitingPlayers <= 8`，不是只数已入座玩家。
- 对局中途进入的人进入 `waitingPlayers`，等待房主安排下一局入座。
- 旁观者只看到自己的等待卡，不显示其他旁观者列表。
- 当前用户处于等待状态时，用 `selfIsWaiting` 隐藏底部自己的骰盅区域，并在桌面左上角显示等待卡。
- 房主在 `ready` 和 `ended` 都能打开排位设置；有在线等待者时同层显示 `等待入座(n)`。
- 等待者入座继续走 `room:waiting:admit`，不要新建并行事件。
- 离线等待者不能被安排入座，也不计入 `等待入座(n)`。
- `ended` 阶段如果有在线等待者，下一局开始控制权交给房主；房主必须先安排在线等待者，离线等待者不阻塞开局。
- 等待玩家被安排入座时要保留 `accountId` 和 `accountDisplayId`，避免入座后账号身份丢失。

## 其他近期逻辑沉淀

- 昵称长度从 1-5 调整为 1-12 个字符，服务端和小程序端校验文案都改为“字符”。
- 房间音效路径从 `/assets/audio/...` 调整为 `/pages/room/assets/audio/...`，相关播放和停止测试要跟着改。
- 创建房间页新增主题卡片预览，并复用 `LOBBY_FLOAT_DICE_ASSETS`、`LOBBY_CREATE_DIE_ASSET`，固定 8 座、无旁观开关、无锁房开关仍是当前发布口径。
- 结算页把“顺”“豹N”拆成独立标签，并新增豹子加成 `+1` 展示；后续结算 UI 改动要同时考虑列表态和弹层态。
- `RoomService.broadcastRoomState` 先刷新回合 deadline 再广播，避免客户端拿到旧 `turnDeadlineTs` 后倒计时异常。
- 小程序已加入 `miniprogram/miniprogram_npm/@babel/runtime/helpers/` 兼容补丁，避免开发者工具 ES6 转换后找不到 runtime helper。
