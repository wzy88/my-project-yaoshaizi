# 2026-04-23 发布前房间逻辑与 UI 沉淀

适用范围：

- 服务端房间状态机：`apps/server/src/engine/room-engine.ts`
- 服务端房间连接层：`apps/server/src/engine/room-service.ts`
- 小程序房间页：`miniprogram/pages/room/room.*`
- 相关自动化回归：`tests/server-room-engine.test.mjs`、`tests/room-mobile-entry.test.mjs`

本文档记录 2026-04-23 发布前确认并实现的关键逻辑、交互和 UI 约定。后续修改房间主链路时，优先按这里的规则判断，不要凭局部代码现象反推产品逻辑。

## 1. 发布目标

- 当前版本目标是尽快稳定上线，不做大范围玩法重构。
- 本阶段重点是修极端情况、补发布前风险边界、减少真人测试反复打包成本。
- 已经跑通的主链路和视觉结构不要随意重构。
- 新增改动必须优先覆盖自动化回归，再做真机体验确认。

## 2. 房间人数和座位口径

- 房间固定 8 个杯位。
- 8 个杯子常驻展示，进几个人就有几个头像。
- 空座位不显示玩家头像，但杯位本身仍保留。
- 创建房间页不再让用户选择人数，文案口径是固定 8 个座位/杯位房间。
- 对局玩家最多 8 人，不额外支持超过 8 人的纯旁观。

## 3. 玩家进入房间

### 3.1 ready 阶段加入

- 房间处于 `ready` 时，新玩家直接加入 `players` 并自动分配空座。
- 房主可在开局前调整座位。

### 3.2 对局中加入

- 房间处于 `rolling`、`calling`、`opening`、`ended` 等非 ready 主流程时，新玩家进入 `waitingPlayers`。
- 等待玩家是旁观/等待状态，不能摇骰、叫牌、开牌、继续下一局。
- 下一局开始前，必须由房主将等待玩家分配到空座后，才成为对局玩家。
- 小程序入口通过“房主工具 -> 等待者入座”触发 `room:waiting:admit`。

### 3.3 等待者入座

- 服务端允许房主在 `ready` 或 `ended` 阶段将等待者入座。
- 不允许在 `rolling/calling/opening` 阶段调整等待者入座，避免破坏当前局结算统计。
- 入座时必须选择 1-8 的空座位。

## 4. 座位调整逻辑

- 房主可在 `ready` 阶段调整座位。
- 房主也可在 `ended` 结算后、下一局开始前调整座位。
- 不允许在 `rolling/calling/opening` 阶段调整座位。
- 座位操作包含：
  - 选中有人座位 -> 点空座：移动玩家。
  - 选中有人座位 -> 点另一个有人座位：交换两人座位。
  - 选中空座 -> 点另一个空座：仅切换选中态。
- 叫牌方向仍属于房间配置，开局后不应随意改；当前重点开放的是座位移动和等待者入座。

## 5. 主动退出、断线与重连

### 5.1 主动退出

- 玩家点击离开房间属于显式退出，不等同于临时断线。
- 如果玩家在 active round 中主动退出：
  - 该玩家标记为离线并等待下一轮清理。
  - 该玩家已经叫过的牌仍有效。
  - 该玩家的骰子仍参与本局开牌统计。
  - 如果只剩 1 个有效在线对局玩家，当前局立即结束并回到 `ready`。
  - 这类中止局不记输赢、不写历史。

### 5.2 轮到主动退出玩家

- 如果轮到某个玩家叫牌时，他已经主动退出：
  - 服务端应快速自动推进，不让其他玩家等完整超时。
  - 有最小合法叫牌时，服务端自动替他叫一手。
  - 已经无合法叫牌时，服务端自动开牌。
- 这只适用于显式退出后的处理，不要扩大到普通临时断线。

### 5.3 临时断线和后台

- 关闭小程序、切后台、网络闪断属于临时断线。
- 临时断线保持当前重连机制，不立即当作主动退出。
- 断线玩家在宽限期内回来，继续使用 `resumeToken` 恢复房间状态。
- 如果轮到临时断线玩家，沿用原有叫牌超时自动处理，不额外加速。

### 5.4 只剩一名有效玩家

- active round 中只剩一名有效在线玩家时：
  - 服务端立即回到 `ready`。
  - 保留房间和剩余玩家。
  - 清空当前局的 lastCall/currentPlayer/骰面等临时状态。
  - 不写入历史，不统计胜率。

## 6. 开牌按钮判断

前端不要只看“轮到我 + 有 lastCall”就显示开牌。

必须同时满足：

- 当前阶段是 `calling`。
- 当前行动人是自己。
- 自己不是等待者。
- 存在上一手叫牌。
- 上一手叫牌人不是自己。
- 上一手叫牌人仍存在于对局玩家列表。
- 在线对局玩家不少于 2 人。

不满足时：

- 快捷开牌按钮不显示。
- 调用开牌操作时给“当前还不能开牌”的产品态提示。

## 7. 结算与下一局

### 7.1 正常情况

- 开牌后进入 `ended`。
- 输家是下一局起始位。
- 输家在线时，输家看到继续/开始下一局能力。
- 其他玩家显示等待。

### 7.2 输家离线或已退出

- 如果输家离线、已退出或等待下一轮清理：
  - 房主可以接管开始下一局。
  - 如果原房主就是离线/退出玩家，服务端应转移房主后由新房主接管。
- 下一局开始前，服务端会清理上一局中 `pendingRemoval` 的玩家。
- 如果清理后不足 2 名在线对局玩家，则回到 `ready`，不强开新局。

## 8. 胜率统计口径

- 只有开牌相关双方计入胜负：
  - 开别人的玩家。
  - 被开牌的上一手叫牌玩家。
- 本局中没有开别人、也没有被别人开牌的玩家，不计输赢。
- 中止局、只剩一人回 ready 的局，不计输赢。

## 9. UI 与视觉规范

### 9.1 总体视觉

- 房间页是游戏舞台，不是普通表单页。
- 桌子和杯位是第一视觉层级。
- 头像、昵称、叫牌气泡贴近对应杯子，形成围桌关系。
- 底部按钮是 HUD，不应遮挡牌桌，也不应抢主视觉。

### 9.2 固定 8 杯位

- 所有布局以 8 个固定杯位为基础，不再按当前人数压缩成紧凑环。
- 玩家换座时，头像应移动到对应座位的真实位置。
- 空座只保留杯子，不出现假头像。

### 9.3 头像和昵称

- 左右两列玩家头像要垂直对齐。
- 左右侧头像大小与 6 点、12 点方向保持一致口径。
- 昵称保持单行展示，不换行。
- 昵称规则为 1-5 个字符，违禁词、广告、联系方式要拦截。
- 昵称空间不足时优先通过字号/样式适配，不要截断成错误昵称。

### 9.4 叫牌气泡

- 所有座位气泡使用统一紧凑尺寸。
- 左右侧气泡与杯子间距要小，只保留轻微空隙。
- 气泡不能遮挡头像、昵称或 12 点方向杯子。
- 气泡尾巴使用圆润、柔和的视觉处理，不用尖锐突兀三角。

### 9.5 右下角按钮

- 右下角按钮包含主行动按钮和开牌快捷按钮。
- 两个按钮风格要统一，椭圆/球形都应有同一套立体质感。
- 按钮文字不换行，字数多时自适应字号。
- 真机底部安全区必须留足，按钮不能被手机边缘吃掉。

### 9.6 左上角菜单

- 左上角入口文案当前为“音效开关”。
- 外轮廓不要过重，避免廉价感。
- 展开面板字体稍大，颜色和层次要更高级。
- 房主工具只在有等待玩家等需要时露出，避免菜单过载。
- 微信 `showActionSheet.itemList` 最多 6 项，菜单分组必须遵守该限制。

### 9.7 安全区与牌桌完整性

- 真机优先保证完整看到整个牌桌下边缘。
- 不同机型下允许整体舞台轻微缩放，但不要改动元素相对位置。
- 底部遮罩不是必须项，避免用厚重遮罩掩盖布局问题。

## 10. 音效和震动

- 房主调座位不播放操作音效，只保留必要的轻反馈。
- 轮到玩家时播放提示音，并配合震动提醒。
- 轮到玩家提示音播放完整，不再截断到 60%。
- 输家提醒音效与普通结算音效区分。
- 结算音效只在结算弹层首次出现时播放，避免重复触发。

## 11. 自动化回归沉淀

本次新增/覆盖的关键自动化点：

- active round 主动退出后只剩 1 人，服务端回到 `ready`。
- 输家离线/已退出后，房主可开始下一局。
- 结算后房主可重新打开排位面板。
- 开牌按钮在上一手是自己、只剩 1 名在线玩家等场景下隐藏。
- `ended` 阶段输家离线时，房主主按钮显示可开始。
- 有等待玩家时，工具菜单暴露房主工具入口。

发布前推荐命令：

```bash
npm test
```

最近一次验证结果：

- `npm test`：166 pass / 0 fail / 1 skip。

## 12. 后续改动原则

- 修改房间状态机前，先判断是“主动退出”还是“临时断线”。
- 修改结算/下一局前，先判断输家是否在线、是否仍在 players、是否 pendingRemoval。
- 修改开牌入口前，必须同步前端显示条件和服务端合法性。
- 修改 UI 前，先检查 8 杯位固定布局、真机安全区、气泡/头像/昵称互不遮挡。
- 每次涉及房间主链路，至少跑 `npm test`，并真机覆盖两台设备分享加入。
